## 1. 背景与范围

**机制一句话**：Dream-RSI 让发现系统自我改进"探索策略"。在线探索产出发现树（每个节点=一次真实尝试的结果）；历史树被当作**免费的回放模拟器**——大量候选策略在旧树上"做梦"评估时只看已记录的结果，**零模型调用**；选出的更优策略再部署回在线，循环往复。

**本次范围**：不动 MiQi 产品代码。在独立仓库（fork）上把机制接到 Claude Code 上端到端验证，产出可复现、可审计的证据，供决策是否在 MiQi 落地。

**为什么选 Claude Code**：它是成熟、可脚本化驱动的 agent（无头 `claude -p` 模式），且原仓库的循环骨架（树/回放/Eq.(1)/选择）已经存在，只需补一个 Claude 适配层即可获得完整的机制验证，而不是先造轮子。

## 3. 验证结果

### 3.1 确认运行（run-dbae5ab3，2026-10-12 17:49–18:48，约 58 分钟）

配置：packing 任务、Claude 后端（`claude-sonnet-5`，无头）、模型写策略修订、2 个世界、每轮最多 2 次并行探索、每次选择最多 3 个策略版本（含现任）。

调用账目：7 次模型调用（5 次发现 + 2 次策略修订）· 15 次历史回放 **且回放中模型/评测器调用 = 0**（机制核心性质，被逐条断言）· 预算 12 用 7、无一次被预算切断。

**策略竞赛（这是核心事件）：**

| 策略 | 历史平均分 V | 结局 |
|---|---|---|
| 手写现任 | 0.200000 | 被替换 |
| **模型修订 #1** | **0.400000** | **部署上线** |
| 模型修订 #2 | 0.400000 | 与之打平（平局保留更早版本） |

**为什么 V 翻倍——因果链完全可对账**（来自落盘的回放轨迹）：现任策略在低预算档位会探入没有后续的分支并**空转 6 轮**（并行惩罚 P=3.0）；模型修订加入了"预算档位控制轮数 + 探测无果立即停止"的逻辑（P=1.0）。质量项相同（0.5），惩罚减半，总分翻倍。

**同一机制的两次对照**：第一轮实验（更早的一次，3 个世界）里模型的两个修订都被正确地拒绝（各 −0.1，因为它们既不响应预算档位又浪费探测）；这次两者都到 0.4。**选择器两次都做出了有据可依的正确决定**——先拒绝差的，后接受好的。

**部署与后续效应**：部署文件与修订文件哈希字节级一致；随后世界 w1 在新策略下产出了**结构不同的树**（节点数 3 vs 2），探索产出 0.224249（其中 1 次调用撞上 900 秒墙钟上限——如实记录为 TIMEOUT，且它已写好的候选文件照常被评了分）。

## 4. 限制与诚实边界

- **单任务、小树**：验证用的是自建 packing 任务（已知解析上界 0.224502965，模型稳定达到），世界只有 2–3 个节点。它证明机制正确、闭环生效，**不构成"广泛任务上自我改进收益"的证据**（这一点与上游仓库的自我声明一致）。
- **独立校验唯一红项**：`worlds.real_discovery` 要求"每一次发现调用都成功"。本运行 5 次调用中 1 次撞上 900 秒上限（如实记录为 TIMEOUT，其已写出的候选仍得 0.224249 分）。这是验收级检查比机制本身更严格，非运行缺陷。
- **模型渠道**：走的是本机已配置的 Claude Code 渠道，非 Anthropic 直连；适配层与模型无关，换任何可用渠道/模型只改命令行参数。
- **上游代码的已知问题未动**：在分析原仓库时发现其 `DiscoveryTree.add_child` 存在多线程竞态（低概率、触发即响亮失败），属上游缺陷，本分支未改动，建议单独反馈上游。

## 5. 成本

- 两轮完整实验 + 冒烟/中止尝试，当日 `claude-sonnet-5` 总账 **$10.05**（按本机 Claude Code 渠道的记账口径）；**单轮完整实验约 $4–5**。
- 机制的经济学要点已实测：一次约 50 分钟的运行里，历史回放的 15 次策略评估**零模型成本**——元层优化几乎免费，这正是 Dream-RSI 相对朴素试错的核心优势。

## 6. 对 MiQi 的结论与建议

**可行性判断：可行，且价值点被实证。** 本次实验就是 MiQi 目标形态的最小翻版——"成熟 agent + 可验证任务 + 记录历史 + 回放评估 + 选优部署"。

落地 MiQi 需要补的两件事（其余地基 MiQi 已具备：历史记录、确定性回放、沙箱、定时任务）：

1. **评估器**——按任务类提供客观评分（可验证的代码任务用测试；文档类用结构/内容校验；开放任务退而用固定 pin 的评审模型做锚）。评估器必须冻结、agent 不可触及。
2. **策略接缝**——把"怎么探索/编排"从 prompt 里抽成一个可离线评估、可整体替换的代码模块。

建议的下一步（如继续）：
- 把策略版本数调到 4（三种角色每轮出齐），换一个**开放式**任务验证多轮复合收益；
- 本次最值得深追的信号：**模型能独立发现并修复现任策略的效率缺陷**——这是"历史+回放"教会策略的、可迁移的探索能力。

## 7. 复现方式

```bash
# 克隆 fork 并进入分支后：
# 1) 离线全套（无需任何模型账号）
.venv/Scripts/python.exe -m pytest -q
.venv/Scripts/python.exe -m ruff check . && .venv/Scripts/python.exe -m mypy src
.venv/Scripts/python.exe -m dream_rsi.cli --project-root . offline-test --outer-rounds 2 --task packing

# 2) 真实运行（需要本机已配置好 Claude Code 认证）
.venv/Scripts/python.exe -m dream_rsi.cli --project-root . run \
    --backend claude --developer llm-claude --task packing \
    --provider "YOUR_PROVIDER" --model "YOUR_MODEL" \
    --outer-rounds 2 --k1 2 --workers 2 --versions 3

# 3) 独立校验（把声明参数换成运行记录的参数）
.venv/Scripts/python.exe tools/verify_run.py --run-id <RUN_ID> \
    --expect-backend claude --expect-developer llm-claude \
    --expect-provider "YOUR_PROVIDER" --expect-model "YOUR_MODEL" \
    --expect-outer-rounds 2 --expect-k1 2 --expect-workers 2 \
    --expect-versions 3 --expect-task packing
```

运行产物（事件流、回放轨迹、评分、部署策略、每次调用的请求/结果证据）全部落盘于 `.runtime/runs/<RUN_ID>/`，可逐条复核。

## 附二：多轮增强版对照（M=4 三角色 + 3 世界，2026-10-13 追加）

参数：每轮选型生成 3 个修订（exploit / explore / balance 三角色齐出）+ 现任，共 4 个候选；3 个外轮 = 3 个世界、2 次竞争性选型。Claude 运行 `m4-claude-1`（92 分钟），Codex 运行 `m4-codex-2`（122 分钟）。

**结果：两个 agent 都完成了"改进→部署→再竞争"的复合循环，且都出现了真实的策略更替：**

| | Claude `m4-claude-1` | Codex `m4-codex-2` |
|---|---|---|
| t=1 获胜者 | **exploit 立场**，V 0.2→0.46 部署 | **balance 立场**，V 0.2→0.46 部署 |
| t=2 结局 | **新一代 exploit 0.525 击败在任** 0.510 —— 连续两代改进 | **在任 balance 0.5467 守擂成功** —— 三个新修订全败（0.493/0.483/−0.017） |
| 世界产出 | 3/3 世界全部达到解析最优 0.224503 | 同左 |
| 独立校验 | 15/16（唯一红 = 一次探索调用撞 900 秒上限，如实记录） | 15/16（同型：一次探索调用撞 1200 秒上限，如实记录） |

**三个值得记录的观察：**

1. **三角色的价值被实证**：两个 agent 的最优修订来自不同立场（Claude=exploit，Codex=balance），另外两个立场的候选都在竞争中落败——如果每轮只生成一个修订，机制有至少一半概率错过最优的那一个。角色多样性是在"扫"策略空间，不是装饰。
2. **渠道故障被机制完整消化**：Codex 运行经受了 6+ 次 8–20 分钟的供应商慢调用；三次压线返回、两次被上限截断后如实记录（且截断前已写出的候选照常得分）。更早的一次 900 秒上限运行因修订调用超时触发了设计内的"响亮阻断"（BLOCKED_EXTERNAL，宁可停机也不带着未知状态继续）——放宽到 1200 秒重跑后完成。**发现→停机→修复→续跑**这条运维链路本身也经过了实战。
3. **护栏缺口的现场案例**：Codex 的开发者 agent 会联网检索（Packomania、StackExchange API 等），甚至直接查询运行的 SQLite registry 来检查分数。运行时信息屏障（策略只能看前缀）未被破坏、静态门照常拦截，但这说明"开发者可读写的边界"依赖进程隔离之外的约定——若要在生产环境收紧，需要给开发者会话加目录级隔离，或在 prompt 中恢复论文原本的反过拟合条款。
